# 0001. アーキテクチャ決定を記録する

## ステータス

承認（2026-11-10）

## コンテキスト

技術の選定や構成について下した判断は、時間がたつと理由が失われやすい。理由がわからないと、後からコードを読む人は、その判断を守るべきか変えてよいかを判断できない。

## 決定

アーキテクチャ上の重要な決定を、Michael Nygard の提唱した形式の Architecture Decision Record（ADR）として `docs/adr/` に記録する。

各 ADR は、タイトル、ステータス、コンテキスト、決定、結果で構成する。

ADR にするのは、後から変えるのが大変な決定や、理由がコードから読み取れない決定に限る。

新しい ADR は、連番を振ったファイルとして追加する。ステータスは「提案」「承認」「置き換え済み（00XX で置き換え）」のいずれかとする。

提案の間は自由に書き直してよい。承認した後は、ステータスの更新を除いて書き換えない。方針を変える場合は新しい ADR を作り、そのコンテキストで置き換える ADR の番号を示す。あわせて、古い ADR のステータスを「置き換え済み（新しい ADR の番号で置き換え）」に更新する。

`docs/adr/README.md` には ADR の一覧を置く。

## 結果

- 判断の背景と理由が、コードと同じリポジトリで管理される。
- 決定のたびに ADR を書く手間が増える。
- 承認済みの ADR は書き換えないため、方針の変遷を後から追える。
