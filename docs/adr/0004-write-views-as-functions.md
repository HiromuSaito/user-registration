# 0004. 画面と API のビューは関数ベースで書く

## ステータス

承認（2026-11-14）

## コンテキスト

ユーザー登録を、登録画面と API の 2 つの入口で提供する。どちらも、同時に登録されたときのエラーを扱うなど、決まった型に収まらない処理を含む。

Django と DRF のビューは、次のどれでも書ける。公式はどれかを推していない。

| 書き方 | Django（登録画面） | DRF（API） |
|---|---|---|
| 関数ベース | 関数 | `@api_view` を付けた関数 |
| メソッドごとに分けるクラス | `View` | `APIView` |
| よくある処理の型を継承するクラス | `CreateView`、`FormView` | ジェネリックビュー（`CreateAPIView`、`ListAPIView`）、`ViewSet` |

AI によるコーディングが広まった今、書く量が多いことは大きな問題ではない。それよりも、人が読んで理解しやすいこと、テストで何を確かめればよいかがわかること、フレームワークの内部の動きに左右されず壊れにくいことを重視する。

検討した案は次のとおり。

- 型を継承するクラス: 書く量が少なく、DRF では API の仕様書も自動で作られやすい。ただし、保存やステータスコードなどの処理が親クラスに隠れるため、読むにも、型から外れる処理を足すにも、テストで確かめるにも、親クラスの知識が要る。
- メソッドごとに分けるクラス: 処理は明示的だが、ビューごとの処理が少ないため、関数の中で分けるのと比べて読みやすさは変わらない。
- 関数ベース: 上から順に読めば、何をして何を返すかがわかる。処理がすべて見えているため、テストで確かめることがコードから読み取れ、親クラスの動きに頼らないので壊れにくい。

## 決定

登録画面と API のビューは、どちらも関数ベースで書く。

## 結果

- 登録画面と API で、ビューの書き方がそろう。
- 型を継承するクラスより、書く量が多くなる。
- API の仕様書は入出力を推測できないため、ビューごとに入出力を宣言する必要がある。
