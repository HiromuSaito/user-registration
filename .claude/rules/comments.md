# コードコメント規約

**コメントには理由を書く。何をしているかは書かない。**

## 原則

- 何をしているかはコードを読めば分かる。コメントで言い直さない。
- **コメントがないと意図が伝わらないと感じたら、コメントを足すのではなく設計を疑う。** 名前を変える・関数に切り出す・クラスを分ける・型ヒントで表す、を先に試す。
- **長さは制限しない。** 伝えるべき理由が複数あるなら複数文で書く。短さを目的にせず、下記の「書かないもの」を書かないことで結果的に短くする。
- コードの行ごとに対応する説明を付けない。

## 書くもの: コードを読んでも分からない理由

```python
# createsuperuser は REQUIRED_FIELDS の外部キーに主キーの値（都道府県コード）を渡すため、
# pref ではなく pref_id として渡す
if "pref" in extra_fields and not isinstance(extra_fields["pref"], Pref):
    extra_fields["pref_id"] = extra_fields.pop("pref")
```

```python
# \d や str.isdigit() は全角数字なども通すので、半角の 0〜9 だけを [0-9] で確かめる
if not re.fullmatch(r"[0-9]+", value):
```

```python
# 件数が多く N+1 になるため、select_related でまとめて取得する
users = User.objects.select_related("pref")
```

一見遠回りに見える書き方や、崩すと壊れる順序など、**知らない人が「整理して直そう」と考えてしまう箇所**に書く。

## 書くもの: 警告を止める理由

`# noqa` や `# type: ignore` には、止めてよい理由を必ず書く。理由がないと、後から読む人は外してよいのか判断できない。

```python
# 要件で null=True が指定されているため DJ001 を止める。空は None に統一する
tel = models.CharField(max_length=20, null=True, blank=True)  # noqa: DJ001
```

止めるルールは `# noqa: DJ001` のようにコードで指定し、`# noqa` だけで全部を止めない。

## 書かないもの 1: コードを言い直すだけのコメント

```python
# NG
# 空ならスキップ
if not codes:
    return
```

説明が必要だと感じたら、コメントを書くのではなく名前を直す。

処理に番号を振って並べるコメントも書かない。

```python
# NG
# 1. 入力を検証する
# 2. メールアドレスを正規化する
# 3. 保存する
```

手順が増えたり順番が変わったりしても番号は直されないので、コードとずれていく。

## 書かないもの 2: これから直す予定

「後でこうする」という予定は基本的にはコードに残さない。Issue や PR を分けたいなど事情があって残したい場合は、`TODO`・`FIXME` を付けて、あとで追いやすいようにする。

## マイグレーション

- `makemigrations` で自動生成したマイグレーションには、コメントを足さない。
- `RunPython` や `RunSQL` など手で書く処理は、通常のコードと同じく理由を書いてよい。
